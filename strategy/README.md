# strategy · 决策层

## 规则模型（2026-10-19 更新，按"只能推自己颜色"）

| 规则 | 实现 |
| --- | --- |
| 红队守左门、黑队守右门 | `config.SIDE_GOAL`（抽签相反就对调） |
| 只能推自己颜色 | 聚类时 `sides=own_side` 过滤，别人颜色的棋子不参与目标 |
| 己方颜色进己方门 → 加分 | `+分值` |
| 对方颜色进己方门 → 扣分 | `-分值 × config.PENALTY_FACTOR`（默认 1.0；细则没定，先按等值扣） |
| 一次推 1~2 枚 | `TARGET_MAX_PIECES = 2`；大簇会被切成"单枚/相邻两枚"的候选，再按净收益/耗时挑 |
| 推头宽度 | `BLADE_WIDTH_MM = 120`（约 2.7 个棋子宽），保证一次只带 1~2 枚 |

**净收益** = 己方分值 − 对方分值 × 扣分系数。净收益 ≤ 0 的簇直接丢掉——推了白亏。

**现场换边**（比赛抽到红/黑临时切换）：

- 实时窗口**右上角两个按钮**，鼠标点一下；
- 或者按键 `1` = 红队、`2` = 黑队；
- 或者启动时 `--side red|black`。

换边会清空场地记忆、缓存和计分（球门和目标颜色都变了），这是预期行为。

把"棋局态势"翻译成"下位机动作"。输入就是 `vision/realtime.py` 里的 `state`，
输出是一条运动指令（`$GOTO/$TURN/$DRIVE/$BLADE/$STOP`）。

**现在没有车、没有真棋子也能验证**——`sim.py` 提供了一个 2D 仿真底盘，
和真车走同一套接口。

## 文件

| 文件 | 作用 |
| --- | --- |
| `commands.py` | 指令定义 + 串口编码（带校验和，与 `firmware/protocol.c` 一致） |
| `fsm.py` | 决策状态机（下面那张图） |
| `sim.py` | 2D 仿真：底盘执行器 / 推板推动 / 计分 / 前视相机仿真 |
| `run_sim.py` | 跑 N 局，打印得分、趟数、脱困次数，可录视频 |

## 状态机

```
IDLE ─start→ SEARCH ─有目标→ APPROACH ─到点→ VERIFY ─还在→ ALIGN
                 ↑                              ↓(目标没了/漂了)
                 │                              └→ SEARCH
                 │                                   ALIGN ─摆正→ BLADE_DOWN ─放板→ PUSH
                 │                                                        ↓
                 └──── CLEARUP ← RETREAT ← DEPOSIT ←── 推进到位 ─────────┘

APPROACH/PUSH/DEPOSIT 卡住或超时 → RECOVER（放板、倒车、转开、目标冷却 20s）→ SEARCH
剩余时间不够跑一趟 → DONE（停车）
```

几个关键设计（都是踩过坑之后才加的）：

| 机制 | 为什么要 |
| --- | --- |
| `VERIFY`（到点后复看一次） | 车开过去要 2~3 秒，目标可能被对手撞走/自己看错；不复看就会"对着空气推" |
| `SEARCH` 扫 3 圈后去堆放区 | 车在角落、棋子在场中间，视野只有 0.8m，不主动过去永远看不见 |
| 目标冷却（blacklist） | 推失败的目标不能立刻重试，否则会在同一个地方反复卡死 |
| 卡住检测只看 `DRIVE` | `GOTO` 会先原地转向，用位移判断会把"正在转"误判成"卡住" |
| 推棋期间暂停记忆登记 | 推的时候棋子一直在动，照常登记会把同一枚记成十几条"幽灵" |
| 推完清掉扫过的走廊 | 不清的话，下一趟会朝棋子原来的位置去推 |

## 跑仿真

```powershell

python strategy/run_sim.py --team red --video       # 只演示红队，录到 vision/data/output/sim.mp4
python strategy/run_sim.py --episodes 10            # 看稳定性
```

### 物理真实性（2026-10-20 补上，之前那版分数作废）

早期仿真没算"车体压到棋子"，所以车能像幽灵一样穿过棋堆，跑出 182 分。
加上车体碰撞（压到棋子会把棋子挤到旁边、车被顶偏并降速）之后：

| 场景（40 秒、只跑红队、窄推 120mm、一次 1~2 枚） | 得分 |
| --- | --- |
| 32 枚集中在中央堆放区（按规则图） | **−8 ~ 10 分**（进区 4 枚，但误推扣分） |
| 32 枚散布全场 | **5 ~ 12 分**（平均 3 趟只成 1~2 趟） |

失败原因（trace 里能看到）：

1. 开过去时**车体把目标撞歪/撞散**，到点复查时"目标不在了"（11 秒那次就是）；
2. 就算目标还在，**1.4m 长推 + 3° 航向误差 = 横向漂 7cm**，120mm 窄推头兜不住，棋子从边上滑掉；
3. 推的过程中会把旁边的对方棋子一起带进门，直接扣分。

**结论：不能"穿堆推"。** 机构必须改成下列之一：

- 从堆放区**外缘**作业，车体不进堆，只让推板探进去把边缘 1~2 枚扒出来；
- 推头加**侧向挡边/梳齿**把棋子兜住（或直接做成 U 形小铲斗，铲起来运走）；
- 推进改成**分段短推**（每 300~500mm 停下复核、修正航向），不要一次盲推 1.4m。

> 仿真里的控制模型仍然很粗（没有轮子打滑、棋子翻滚、真实摩擦），**绝对分数不要当真**；
> 但它能可靠说明方向和趋势——"车直接穿过棋堆再开始推"这条路走不通。
> 最快的验证办法：拿 32 枚棋子在桌上摆好，用一块 120mm 的纸板推一推，看会不会滑/散（半小时）。

## 接到真车上（三步）

1. **输入**：`realtime.py` 里已经有 `state`（`game.build_state` 的输出）。
   把 `engine.process(frame)` 返回的 `state` 直接喂给 `fsm.update(...)`。
2. **输出**：`fsm.update()` 返回的 `Command` 用 `cmd.encode()` 变一行字符串，
   通过串口发给 STM32（替换掉 `sim.py` 里的 `SimChassis.send`）。
3. **完成信号**：`action_done` 用下位机回传的 `$P,...,done` 里的 `done`；
   位姿也用 `$P` 里的 x/y/h。若暂时没有 done 信号，可以先用"位姿到位 + 超时"判断。

`fsm.update(gs, pose, now, action_done, opponent=None, memory=mem)` 的参数：

| 参数 | 说明 |
| --- | --- |
| `gs` | `game.build_state()` 的返回值（含 `plans`） |
| `pose` | 车在场地上的位姿 `(x, y, heading_deg)` |
| `now` | 秒（单调递增） |
| `action_done` | 上一条指令是否完成 |
| `opponent` | 对手车位置 `(x, y)`，可选；用来避开"我要去的对准点" |
| `memory` | `game.FieldMemory`，用来在推完后清走廊 |

## 已知限制（下一步）

1. **没有路径绕行**：现在只给"对准点+朝向+推进距离"，遇墙/对手靠 `RECOVER` 兜底。
   3m×2m 场地直线够用，但对手堵路时需要 A* 或简单绕行。
2. **没有对手博弈**：只做"离对手远一点"，没有"抢它正在推的那堆"。
3. **不校验投放结果**：推完就默认成功。以后可以用视觉看到球门区棋子数增长来确认。
4. **仿真乐观**：见上表说明。真车上线后，用 `docs/测试记录.md` 记录真实得分。

## 窄推的可展示演示（2026-10-20 新增）

`push_demo.py` 是**独立于 `sim.py` 的第二套物理模型**，专门用来回答
“窄推到底能不能一次只推 1~2 枚”：

- 棋子之间会互相挤开（圆-圆碰撞），不能再从棋堆里“穿过去”；
- 推板必须真的扫到棋子才推得动（没有“200mm 外瞬移到板前”的作弊）；
- 车体压到棋子会把棋子顶开、车被顶偏；
- 推板带 10mm 侧挡边，进入 100mm 内槽的棋子会被夹住。

### 跑法

```powershell
python strategy/push_demo.py --layout grid --rule any --video
python strategy/push_demo.py --layout pile --rule own --seconds 90 --no-render
```

### 结果（`--layout grid`，16 个独立取棋工位，每工位 2 枚）

| 指标 | 数值 |
| --- | --- |
| 回收 | 32 / 32 枚 |
| 得分 | 182 分（公开赛题文本：任意棋子按面值） |
| 趟数 | 16 趟，每趟 2 枚 |
| 用时 | 186.5 s |
| 失败 / 车体碰撞 | 0 / 0 |
| 平均节拍 | 11.6 s/趟 |

**这是“机构节拍 + 重复精度”演示，不是开局堆态的自主比赛成绩。**

### 官方开局堆态的真实可达性（3 个随机种子）

| seed | 具备“车不进堆、直线推到门”完整走廊 | 能靠近但推送线会扫到邻子 | 车根本进不去 |
| --- | --- | --- | --- |
| 7 | 0 / 32 | 13 | 19 |
| 11 | 0 / 32 | 13 | 19 |
| 23 | 1 / 32 | 14 | 17 |

结论：

1. **窄推只能剥最外缘。** 想推左边，车必须站在棋子右边，而右边就是棋堆内部；
2. 从堆外往里推，推的是一整排，不是 1~2 枚；
3. 若细则真的是“只能推己方颜色、推错扣分”，A 方案在开局堆态基本不可用，
   应转向 **B：下探式夹爪**（模型见 Codex 输出目录 `model_iso_B.png` 等）。

规则原文目前只写“按棋子对应分值累计得分”，**没有写颜色限制**；
这一点必须先向组委会确认，再决定是否把推板加宽成“宽扫堆”。

## 宽推扫堆（2026-10-22 新增，当前主方案）

规则只允许“推板、滚轮等推进机构”，抓钩/夹爪属于灰区；因此主方案改为
**300mm 折叠宽推**：发车 200mm，工作时展开 300mm，从棋堆右侧整排扫向左侧球门。

程序：`strategy/wide_push.py`

```powershell
python strategy/wide_push.py --seconds 42 --video
```

真实棋堆（`vision/data/output/pipeline.json`，32 枚、总分 179）结果：

| 指标 | 数值 |
| --- | --- |
| 总分 | 179 / 179 |
| 进区 | 32 / 32 枚 |
| 趟数 | 3 趟（y=1000 → 1200 → 800） |
| 用时 | 35.3 s |
| 效率 | 5.1 分/秒 |

### 两套算法

| 模式 | 程序 | 适用 |
| --- | --- | --- |
| ALL 任意颜色 | `wide_push.py` | 规则不分颜色；宽推扫堆 |
| OWN 只推红 | `push_demo.py --rule own --side red` | 只算己方颜色；120mm 窄推 |
| OWN 只推黑 | `push_demo.py --rule own --side black`（镜像待回归） | 同构镜像配置 |

> 规则没有写颜色限制，也没有写“只能推己方”。
> 已把两种规则都做成可切换参数；宽推的得分效率比窄推高约 5 倍。
